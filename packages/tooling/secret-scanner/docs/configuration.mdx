# Configuration

Every entry point (`scan`, `scanFiles`, `scanString`, `listRules`, `inspectRuleset`) accepts the same grouped `ScanOptions` object. Keys are namespaced by concern — `config`, `walk`, `rules`, `baseline` — plus a few truly cross-cutting flags at the root.

## Shape

```typescript
export interface ScanOptions {
    baseline?: string;
    concurrency?: number;

    config?: {
        extendBundled?: boolean;
        heuristics?: {
            lockFile?: boolean;
            notAlphanumericString?: boolean;
            potentialUuid?: boolean;
            sequentialString?: boolean;
        };
        inline?: GitleaksConfig;
        minConfidence?: "low" | "medium" | "high";
        onlyVerified?: boolean;
        path?: string;
        validate?: boolean;
    };

    maxArchiveDepth?: number;
    maxDecodeDepth?: number;

    redact?: boolean;

    rules?: {
        enable?: string[];
        exclude?: string[];
        include?: string[];
    };

    verbose?: boolean;

    walk?: {
        excludeFromFiles?: string[];
        excludePatterns?: string[];
        gitignore?: boolean;
        includeHidden?: boolean;
        maxFileSize?: number;
    };
}
```

## Root-level

| Option             | Type              | Default | Description                                                                                                                                         |
| ------------------ | ----------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `baseline`         | `string`          | —       | Path to a JSON array of `Finding` objects. Matches are suppressed by fingerprint.                                                                   |
| `concurrency`      | `number`          | auto    | Rayon worker threads. `0` or `undefined` uses rayon's global pool.                                                                                  |
| `gitleaksIgnore`   | `string \| false` | —       | Path to a `.gitleaksignore` to honour. See [Suppression](./suppression.mdx#5-gitleaksignore).                                                       |
| `inlineAllow`      | `boolean`         | `true`  | Honour `gitleaks:allow` / `pragma: allowlist` markers. `false` audits them.                                                                         |
| `maxArchiveDepth`  | `number`          | `0`     | Nesting depth for zip / tar / gzip / tar.gz scanning. `0` leaves archives skipped as binary files. See [`maxArchiveDepth`](#maxarchivedepth) below. |
| `maxDecodeDepth`   | `number`          | `2`     | Layers of base64 / hex / percent-encoding to decode and rescan. `0` disables decoding. See [`maxDecodeDepth`](#maxdecodedepth) below.               |
| `redact`           | `boolean`         | `false` | Mask the `match` and `secret` strings in every emitted finding.                                                                                     |
| `reportSuppressed` | `boolean`         | `false` | Return suppressed findings in `suppressed` from the `*Detailed` scans.                                                                              |
| `verbose`          | `boolean`         | `false` | Print skipped-rule diagnostics to stderr on the first call.                                                                                         |

### `maxArchiveDepth`

Archives are opened in memory and their entries scanned like files, like gitleaks' `--max-archive-depth`. It is off by default because it costs time and changes results for existing setups.

- **Formats**: zip (stored and deflate), tar, gzip and tar.gz. 7z, xz, bzip2 and zstd aren't opened.
- **Detection by content**: archives are recognised by their magic bytes, not their extension. `notes.7z.txt` holding text is scanned as text, and a zip named `payload.dat` is still opened.
- **Depth**: `1` opens archives found on disk, `2` also opens archives inside them, and so on, up to 8. A gzip stream wrapping a tar counts as one level, so a zip inside a `.tar.gz` needs `2`.
- **Virtual paths**: findings report `file` as `<archive path>!<entry path>`, e.g. `release.tar.gz!vendor/inner.zip!deploy/.env`, gitleaks' `!` separator. A plain `.gz` file has one entry, named after the gzip header's file name or the archive name without `.gz`. Rule `path` regexes and allowlist `paths` see the full virtual path.
- **Entry names**: `\` becomes `/`, control characters are removed, and `.`, `..`, empty and drive-letter components are dropped, so `../../etc/passwd` is reported as `etc/passwd`. Names are only labels; nothing is extracted to disk.
- **Limits** (per archive on disk, across all nesting levels): every entry obeys `walk.maxFileSize` (as does the archive file itself), 256 MiB decompressed in total, 10,000 entries. An entry or gzip stream that expands more than 100x its compressed size, past the first 1 MiB, is a decompression bomb and is skipped. Hitting the total-bytes cap stops the archive; the findings found so far are kept.
- **Skipped entries**: directories, symlinks and binary entries (a NUL byte in the first 8 KiB) are ignored, the same rule as for files. Entries over a size limit or flagged as bombs are listed in `skipped` of `scanDetailed` / `scanFilesDetailed` as `"too-large"` under their virtual path, encrypted or unreadable entries as `"io-error"`, and an archive whose walk stopped at the total-bytes or entry cap under its own path as `"too-large"`.
- **Suppression**: archive entries go through the same allowlists, inline markers, baseline and `.gitleaksignore` as files, matched against the virtual path.

Archive scanning applies to `scan` and `scanFiles`. `scanString` and git history scans don't open archives.

### `maxDecodeDepth`

Secrets are often committed in encoded form, for example a base64-wrapped API key or a Kubernetes `Secret` whose `data:` values are base64. The scanner looks for encoded segments, decodes them, and rescans the decoded text, like gitleaks' `--max-decode-depth`:

- **Encodings**: base64 (standard and url-safe, at least 16 chars), hex (at least 32 chars), and percent-encoding.
- **Acceptance**: a segment is decoded only when the result is valid UTF-8 with no control characters other than tab, CR and LF. Non-ASCII text is accepted. Binary data such as images, hashes and ciphertext is skipped.
- **Context**: the decoded text is rescanned together with up to 256 bytes of its original line, so `password: <base64>` still matches keyword rules.
- **Recursion**: each level looks for further encoded segments inside the decoded text. `2` (the default) covers one layer of wrapping on top of the usual encoding. `0` turns the pass off.
- **Memory cap**: decoded output is limited to 4 MiB per file across all levels.

A finding from decoded text reports the line and column of the **original encoded span**. Its `match` and `secret` hold the decoded value, and `decoded` lists the encoding chain, outermost first:

```typescript
const [finding] = await scanString(`token: ${Buffer.from(key).toString("base64")}`, "secret.yaml");
// finding.decoded === ["base64"], finding.secret === key
```

Plain findings are unaffected. They keep the same positions, order and fingerprints with or without decoding.

## `config` — rule source + validation

| Option          | Type                          | Default | Description                                                                                                               |
| --------------- | ----------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------- |
| `extendBundled` | `boolean`                     | `true`  | Layer the user ruleset on top of the bundled set. `false` replaces it entirely.                                           |
| `heuristics`    | `object`                      | all on  | Toggle post-detection false-positive filters. See [heuristics](#heuristics--post-detection-false-positive-filters) below. |
| `inline`        | `GitleaksConfig`              | —       | Pre-parsed config object. Fastest path, no file IO.                                                                       |
| `path`          | `string`                      | —       | Path to a JSON file (gitleaks-compatible shape). Parsed once and cached.                                                  |
| `minConfidence` | `"low" \| "medium" \| "high"` | —       | Drop rules below this author-declared confidence floor. See [Confidence](#minconfidence) below.                           |
| `validate`      | `boolean`                     | `false` | Live-verify each finding against its provider's API after detection.                                                      |
| `onlyVerified`  | `boolean`                     | `false` | With `validate: true`, drop every finding whose validation is not `"verified"`.                                           |

### Precedence

1. `config.inline` wins when both `inline` and `path` are set.
2. The resulting user config layers on top of the bundled ruleset unless `extendBundled: false`.
3. Opt-in rule bundles (e.g. `tag:preset:weak-passwords`) ship disabled-by-default inside every ruleset; `rules.include` is the only gate.

### `minConfidence`

Every rule may carry an optional `confidence` field (`"low"`, `"medium"`, `"high"`). Rules without an explicit label are treated as `"low"`. Setting `minConfidence` drops rules below the floor:

| Floor      | Drops                                                            |
| ---------- | ---------------------------------------------------------------- |
| unset      | Nothing — every loaded rule fires.                               |
| `"low"`    | Nothing (equivalent to unset).                                   |
| `"medium"` | Rules declared `"low"`, **plus** every rule with no declaration. |
| `"high"`   | Rules declared `"low"` or `"medium"`, plus every unlabeled rule. |

Every bundled gitleaks rule ships unlabeled, so `"medium"` or `"high"` drops the entire stock ruleset. Use this flag against a curated config of your own, or when you opt into a preset that ships labels.

### `heuristics` — post-detection false-positive filters

Four heuristics (ported from [detect-secrets](https://github.com/Yelp/detect-secrets)) run after rule detection and drop high-confidence placeholders before returning. All four default to **on**; set the individual key to `false` when you need the raw match set — typical only when scanning a curated fixture that legitimately contains UUID-shaped or all-dash values.

| Key                     | Default | Drops findings where …                                                                                                                                                                                                                                                                    |
| ----------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lockFile`              | `true`  | file basename is a known lock file (28 entries: `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `go.sum`, `flake.lock`, `gradle.lockfile`, `.terraform.lock.hcl`, …). Lock files are regenerated from manifests and churn constantly; scanning them almost always produces noise, not leaks. |
| `sequentialString`      | `true`  | the secret is a substring of a standard character sequence (`abcdefgh`, `12345678`) or a single repeating character (`AAAAAAAA`, `00000000`). Short secrets (<6 chars) are always allowed.                                                                                                |
| `potentialUuid`         | `true`  | the secret matches the canonical 8-4-4-4-12 UUID shape. In practice UUIDs are object identifiers (trace, request, user) rather than credentials.                                                                                                                                          |
| `notAlphanumericString` | `true`  | the secret contains zero ASCII alphanumerics (`*****`, `------`, `//////`) — almost always a masked-out placeholder captured by a greedy regex.                                                                                                                                           |

```typescript
// Keep UUID-shaped findings when auditing a system that uses UUIDs as API keys.
const findings = await scan([process.cwd()], {
    config: { heuristics: { potentialUuid: false } },
});
```

The filters are intentionally conservative: every entry has to be wrong in a very specific way before it drops. If you hit a false negative you suspect a heuristic caused, toggle the one you suspect off and compare.

For help detecting secrets that span multiple lines in YAML (where the raw scan never sees the full value), see the complementary [`transformYamlBlockScalars`](./api.mdx#transformyamlblockscalarscontent) helper — it's opt-in because it requires reading files in JS rather than through the Rust walker.

### `validate` and `onlyVerified`

`validate` turns on live verification — every finding whose rule declares an HTTP validator is checked against the provider's own API after detection. Cost: one HTTP request per finding (per-host concurrency capped at 4, global at 8). Default `false`, so scans stay offline-safe.

Supported today: Kingfisher-style HTTP validators with `StatusMatch` / `WordMatch` response matchers. Other kinds (gRPC, multi-step HTTP, checksum) surface as `validation: "skipped"` on the finding and pass through unfiltered. Non-HTTP validators (AWS STS, MongoDB, MySQL / Postgres, …) require optional peer-deps — call `listRequiredValidators()` (or `vis secrets --list-validators`) to see which the current ruleset references.

`onlyVerified: true` then filters the emitted set down to findings whose `validation === "verified"` — useful for CI gating where a suspect match that can't be verified is not a blocker.

> **Warning:** `validate: true` sends the candidate secret to the provider. Some providers page their security team on failed auth attempts. Only enable on repos you own or have explicit authorisation to test.

## `walk` — filesystem traversal

| Option             | Type       | Default | Description                                                                                                         |
| ------------------ | ---------- | ------- | ------------------------------------------------------------------------------------------------------------------- |
| `excludeFromFiles` | `string[]` | `[]`    | Paths to `.gitignore`-syntax files to honor in addition to `.gitignore` (for example `.secretsignore`).             |
| `excludePatterns`  | `string[]` | `[]`    | Inline gitignore-syntax lines layered on top of `.gitignore`. Supports negation, directory markers and leading `/`. |
| `gitignore`        | `boolean`  | `true`  | Respect `.gitignore`, `.ignore` and global excludes via the `ignore` crate.                                         |
| `includeHidden`    | `boolean`  | `false` | Visit dotfiles and hidden directory entries.                                                                        |
| `maxFileSize`      | `number`   | 10 MiB  | Skip files larger than this (in bytes). Files above the threshold never enter the detector.                         |

Only `scan()` runs the walker. `scanFiles()` takes a fixed list and bypasses it; there the JS wrapper applies `excludePatterns` / `excludeFromFiles` via the `ignore` npm package so the two code paths behave the same.

## `rules` — id + tag filters

| Option    | Type       | Default | Description                                                                                                            |
| --------- | ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------- |
| `enable`  | `string[]` | —       | **Additive.** Turn on opt-in rules (e.g. `tag:preset:weak-passwords`) without restricting output. Defaults still fire. |
| `include` | `string[]` | —       | **Whitelist.** Only emit findings matching these ids/tags. Implies enablement for opt-in rules referenced here.        |
| `exclude` | `string[]` | —       | **Blacklist.** Drop findings matching these ids/tags. Doesn't enable anything.                                         |

`tag:<name>` entries expand to every rule carrying that tag at config-load time. An unknown tag throws with a list of known tags — catches typos at the boundary. Common tags: `tag:preset:weak-passwords`, `tag:preset:password-manager`.

**Pick the right knob:**

- "enable the weak-passwords rules alongside my normal scan" → `rules.enable: ["tag:preset:weak-passwords"]`
- "scan **only** for password-manager exports" → `rules.include: ["tag:preset:password-manager"]`
- "keep defaults but mute `generic-api-key`" → `rules.exclude: ["generic-api-key"]`

## `baseline` — fingerprint suppression

Set `baseline` to the path of a JSON array of `Finding` objects. Any finding whose content-hash fingerprint — SHA-256 over `(secret, ruleId, file)` truncated to 16 hex chars — already appears in the baseline is suppressed. Because the fingerprint hashes content rather than position, the entry survives line shifts inside the file; it only invalidates when the secret itself, the rule, or the file path changes.

Legacy gitleaks-style baselines using the `<file>:<ruleID>:<startLine>` form keep suppressing correctly on read, so migrating to the content-hash form can happen at your own pace via `vis secrets --update-baseline`.

A missing file is treated as an empty baseline; a malformed file is ignored with a stderr warning — scans never fail because of a broken baseline.

## Gitleaks-compatible schema extensions

The config shape mirrors gitleaks' TOML schema. A few fields are ours (safe additions):

| Field             | Scope     | Description                                                                                                     |
| ----------------- | --------- | --------------------------------------------------------------------------------------------------------------- |
| `priority`        | Rule      | Integer (default `0`). When two rules match the same byte span, the higher priority wins (`#1997`).             |
| `preRegexReplace` | Rule      | Ordered `[{ from, to }, …]` regex replacements applied to the scan buffer before the rule's main regex runs.    |
| `targetRules`     | Allowlist | When non-empty, the allowlist only applies to findings whose rule id is in this list (gitleaks schema `#1919`). |

Gitleaks' own `required` / `skipReport` composite-rule fields are supported too, see [Composite rules](#composite-rules-required-skipreport).

### Commit allowlists

`allowlists[].commits` (gitleaks schema) applies only to git-history scans (`scanGitHistory`, `vis secrets --history`). List full 40-character SHAs; case is ignored.

```json
{
    "allowlists": [
        { "description": "rotated in INC-123", "commits": ["9f1c2e4b7a0d3c5e8f6a1b2c3d4e5f60718293a4"] },
        { "commits": ["0a1b2c3d4e5f60718293a4b5c6d7e8f9a0b1c2d3"], "targetRules": ["generic-api-key"] }
    ]
}
```

- A global allowlist without `targetRules` skips the listed commits entirely.
- A global allowlist with `targetRules`, or a rule's own allowlist, drops only those rules' findings in the listed commits.
- With `condition = "AND"`, an allowlist that also lists `paths`, `regexes` or `stopwords` is not matched against commits.

## Composite rules (`required`, `skipReport`)

Gitleaks 8.28+ composite rules load unchanged. A rule with a `required` list (TOML `[[rules.required]]`) is reported only when every required rule also has a finding in the same file. Key names are gitleaks' own, so a parsed `gitleaks.toml` (`[[rules.required]]` becomes the `required` array) works as is:

```json
{
    "rules": [
        {
            "id": "aws-secret-access-key",
            "regex": "(?i)aws_secret_access_key\\s*=\\s*([A-Za-z0-9/+]{40})",
            "secretGroup": 1,
            "required": [{ "id": "aws-access-key-id", "withinLines": 5 }]
        },
        {
            "id": "aws-access-key-id",
            "regex": "\\b((?:AKIA|ASIA)[A-Z0-9]{16})\\b",
            "skipReport": true
        }
    ]
}
```

| Field                      | Description                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `required[].id`            | Id of a rule that must also match in the same file.                                                  |
| `required[].withinLines`   | Max distance between the start lines of the two findings.                                            |
| `required[].withinColumns` | Max distance between the start columns. Compared **only when both findings start on the same line**. |
| `skipReport`               | The rule still runs, so other rules can require it, but its own findings are never emitted.          |

Proximity rules:

- No `withinLines` / `withinColumns`: a finding anywhere in the file counts.
- Same line: `withinColumns` (if set) bounds the column distance.
- Different lines: only `withinLines` applies. `withinColumns` is never compared across lines (upstream gitleaks fixed the same bug in six PRs, #2123 to #2255). A rule with only `withinColumns` therefore needs the required finding on the same line. This differs from the "rectangular" area the gitleaks README describes for both bounds: a dependency on the next line is not rejected just because it starts at a different column.

A reported finding carries `requiredFindings`: for each required id, the nearest finding that satisfied it (redacted with `redact: true`). The check runs per file, per archive entry and per `scanString` buffer, on the findings before the same-span dedup, so a required finding counts even if it is `skipReport` or itself a composite rule. An allowlisted or inline-allowed finding never satisfies a requirement, as in gitleaks. A satisfied composite finding wins the same-span dedup against any other rule matching the exact same span, whatever its priority; the other rule is listed in `alternateMatches`. A composite `generic-api-key` is also never dropped by the generic-overlap filter.

A rule whose `required` names a rule that isn't loaded (unknown id, failed regex, or filtered out by `minConfidence` or opt-in gating) can never match. It is dropped and listed by `inspectRuleset()` with the reason, and `verbose: true` prints it.

When you extend the bundled ruleset, a user rule with a bundled rule's id but **no `regex` or `path`** extends that rule instead of replacing it: your fields (such as `required` or `skipReport`) are added, `keywords` and `tags` are merged and allowlists are appended (gitleaks #2024). A user rule with its own `regex` or `path` still replaces the bundled one.

### `required` vs. Kingfisher `dependsOnRule`

Both pair related secrets, at different stages:

- `required` gates **detection**: the primary finding is not reported at all without its dependency nearby.
- `dependsOnRule` (bundled Kingfisher rules) only feeds **validation**: the finding is always reported, and with `config.validate: true` the dependency's secret is passed to the validator as a template variable. If no dependency finding is reported in the same file, validation is `"skipped"`.

`dependsOnRule` looks up reported findings, so it doesn't see findings of a `skipReport` rule. Don't mark a rule `skipReport` if a `dependsOnRule` validator needs it.
